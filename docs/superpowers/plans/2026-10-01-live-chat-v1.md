## Key decisions

- **One process, memory state, bounded.** `LIVE_MAX_CONN` (5,000) sockets, 5 per player, 40 per IP; channel ring
  buffers of 50 messages for at most 2,000 channels (LRU); member caches LRU; every limiter table pruned.
- **Identity.** pid = `sha256('pid:' + sid)[:16]` (the Phố nghề id, `game/social.pid_of`). Name: the account's
  display name, else the guest's character name (`leaderboard_players`), else the Phố nghề name. No name → can
  read, cannot post. Avatar: `profiles.avatar`. The service never reads a save.
- **Age** (new sessions read-only on Cả phố for 10 minutes): born before today (`stat_births`), else the oldest of
  `accounts.created_at`, `profiles.created`, the first `stat_play.first_at`.
- **Cả phố** is a room the client joins while it is on screen (`join {ch:"town"}`), so fan-out reaches viewers
  only. Slow mode 10 s per player (server-enforced; the error carries `wait`, the send button counts down).
- **DMs** need `friends` both ways and no block (`blocks` by pid or `marriage_blocks` by sid, either direction).
  Offline recipient → one `push_queue` row (kind `chat`, the player's `social` preference, ≤ 6 unsent) at most
  once per 10 minutes per chat (`chat_members.pushed_at`).
- **Groups**: owner creates, invites friends, ≤ 20 members, owner removes, members leave.
- **Messages are kept.** Delete own → text emptied, `deleted=1`. 3 distinct reports → `hidden=1` until an admin
  decides (`hidden=2` hidden, or back to 0; `reviewed_at` set). Admin changes reach the service by
  `NOTIFY mnl_live` (PostgreSQL); the service also re-checks its buffers when the LISTEN connection reconnects.
- **Restart.** SIGTERM → every socket gets close code 1012; clients reconnect with jitter and backoff 1, 2, 4… 15 s
  and resume with the last message id they hold per open channel (`hello {resume: {ch: id}}`).
- **Switches** `LIVE_CHAT`, `LIVE_STREET`, `LIVE_DATING` are read by the live service and sent in
  `welcome.flags`. All off → the service says so and closes; the client then waits 10 minutes before trying again.
  Before the first welcome ever arrives (no service yet), the client retries slowly (1 min → 10 min), so the game
  server never sees a reconnect storm.

## Production (the owner runs these)

1. **Python library** (on the server, or download elsewhere and `install`):
   `scripts/vendor_websockets.sh /opt/mot-ngay-lam-nghe/shared/pyvendor` (pure-Python wheel `websockets==17.1`,
   sha256 `f2210811…0c23` checked). psycopg is already there (`python3-psycopg` + pyvendor).
2. **Release** (quiet, as 1.0.0 with notes): the game server of this release creates the new tables at start-up
   (`SCHEMA_VERSION` 5: `chat_channels`, `chat_members`, `chat_messages`, `chat_mutes`, `chat_prefs`,
   `live_effects` + their indexes; nothing existing changes). Without `LIVE_URL` the page never opens a socket,
   so the release is safe before the next steps.
3. **Env** `/etc/mot-ngay-lam-nghe/live.env` (root:root 600) from `deploy/live/live.env.example`
   (`LIVE_CHAT=1`, `LIVE_STREET=0`, `LIVE_DATING=0`, `LIVE_ORIGINS=https://phocochuyen.io.vn,https://www.phocochuyen.io.vn`,
   `LIVE_TRUST_PROXY=1`). `DATABASE_URL` comes from `pg.env`.
4. **systemd** `deploy/live/mnl-live.service` → `/etc/systemd/system/`; set `User=`/`Group=` and the sandbox
   lines like `systemctl cat mot-ngay-lam-nghe`; `systemctl daemon-reload && systemctl enable --now mnl-live`;
   check `curl -s http://127.0.0.1:8770/live/health`.
5. **nginx** `deploy/live/nginx-live.conf` (`location = /live`, Upgrade headers, `proxy_read_timeout 75s`) in the
   443 `server {}` of `/etc/nginx/sites-enabled/phocochuyen`; `nginx -t && systemctl reload nginx`. Check
   `worker_connections` (each socket holds two nginx connections).
6. **Turn the page on**: `LIVE_URL=/live` in the game's environment (e.g. a drop-in
   `/etc/systemd/system/mot-ngay-lam-nghe.service.d/live.conf` with `[Service]` `Environment=LIVE_URL=/live`),
   `systemctl daemon-reload`, then a gap-free restart: `mnl-rolling-release --to $(readlink -f /opt/mot-ngay-lam-nghe/current)`.
7. **Rolling releases** now restart `mnl-live` after the game when the unit is enabled (`deploy/rolling_release.sh`;
   copy it to `/usr/local/sbin/mnl-rolling-release`). Switch a phase off: edit `live.env`, `systemctl restart mnl-live`.
8. **Load test before switching on** (scratch database, never the game's):
   `sudo -u postgres createdb -O <db user> mnl_loadtest`, then
   `PYTHONPATH=/opt/mot-ngay-lam-nghe/shared/pyvendor python3 scripts/live_load.py --db-url postgresql://<user>:<pw>@127.0.0.1:5432/mnl_loadtest --conns 2000`,
   then `dropdb mnl_loadtest`. It starts its own live service on a free port.

Measured locally (Apple M-series, client and service on one machine, 60 s steady, 5 Cả phố messages/s from 50
chatters, ~4 sockets/s churning, everyone on Cả phố): 2,000 sockets on PostgreSQL 16: delivery p50 11.7 ms,
p95 26.4 ms, p99 30.4 ms; live process 8.3% of one core on average (peak 18.9%), RSS 82 MB, no errors. SQLite:
p95 24.7 ms, 7.4%, 76 MB. Headroom run: 4,800 sockets at ~12 messages/s: p95 61.5 ms, 25% of a core, 142 MB.

## Extension points for phases 2 and 3

- **Features** (`live/protocol.py`): a feature is an object with a name, a switch (`flag`: `chat`, `street`,
  `dating`), frame handlers marked with `@on("move", rate=(4, 1.0))` (`from live.protocol import Feature, on,
  LiveError`; a handler returns a reply frame or raises `LiveError(code, msg, **extra)`), and optional hooks
  `start()`, `on_hello(conn)`, `welcome(conn)` (extra welcome fields), `on_close(conn)`, `on_gone(player)` (last
  socket gone after the grace), `tick(now)` (every second) and `on_notify(event)` (admin NOTIFY events).
  Per-socket and per-player state: `conn.ext`, `player.ext`. `live/app.py` registers `ChatFeature`; phase 2 adds
  `StreetFeature` (`live/street.py`), phase 3 `DatingFeature` (`live/dating.py`), each one line in
  `FEATURES`. A frame for a feature whose switch is off gets `error {code: "off"}`. Handler names are global:
  phase 2 owns `move`, `emote`, `say`, `sit`; phase 3 owns `queue`, `answer`, `heart`.
- **Rooms** (`live/hub.py` `Room`): a set of connections with a capacity, an optional ring buffer, and
  `send(frame, skip=…)` that serializes once and applies the slow-client cutoff and the block filter.
  `hub.room(id, cap=…)` creates or returns one; `hub.rooms_with_prefix("street:boho:")` lists instances so
  "join the fullest instance with room" is a few lines. Cả phố is `Room("town")`; a street instance would be
  `Room("street:boho:1", cap=20)`, a café table `Room("table:<id>", cap=4)`, a date `Room("date:<id>", cap=2)`.
  A room's `on_empty` callback lets a feature drop instance state; `room.data` holds its state (positions,
  seats); `hub.drop_room(id)` removes it. Moves never touch the database.
- **Stored talk** (`app.chat.store_message(player, channel, text, limit, lines)`): filters, mute check,
  duplicates, insert, returns the `msg` frame (the caller sends it to its room). Street speech bubbles and date
  chat reuse it with their own channel ids (`street:<place>`, `date:<id>`) and register
  `app.chat.route('street:', audience=lambda ch: [rooms…], can_read=lambda player, ch: bool)` so deletes,
  reports (3 → hidden), admin hide/keep and history work for them unchanged. The admin tab lists them by the
  channel prefix.
- **Presence** (`hub.online(pid)`, `hub.visible(pid)`, `hub.conns_of(pid)`): phase 2/3 know who is online and
  shown as online; the matcher pairs only online players.
- **Blocks** (`hub.blocked(a_pid, b_pid)`): both directions, `blocks` and `marriage_blocks`.
- **Rewards** (`live/effects.py` `grant(db, sid, kind, amount, key, data, cap)`): inserts a `live_effects` row
  (`id` = the idempotency key, status `pending`) when the daily cap for that kind allows it. Phase 3 adds
  `game/live_effects.py` `on_load(store, token, state)` called from `/api/bootstrap` beside
  `system_gift.on_load`, applying each pending row through `Store.command` with an internal action and the fixed
  request id `live-<id>` (the `system_gift` pattern: paid once), then `status='applied'`.
- **Client** (`public/js/v4/live.js`): `live.on(type, fn)` for any server frame, `live.send(frame)`,
  `live.flags`, `live.me`, `live.friends` (with `on`), `live.unread()`; an entry point is drawn only when its flag
  is on (the chat's: `liveNav()` in app.js `navItems`, the scene button). The chat dialog (`v4/chat.js`) is
  separate; phase 2/3 add their own dialogs or scenes the same way and open them from a tap on a friend or a
  menu entry. No guide, tips or intro screens in any phase (owner, 01/10): icons, short labels, one-line empty
  states.
- **Menu**: the chat adds one `navItems` entry (`liveChat`, icon `chats`) and `liveChat` in `RAIL_MAIN`; the
  `menu` branch can move that one line into its "Người quen & bạn bè" or "Khu phố" hub.

## Phase 3: "Bạn muốn hẹn hò?" (branch `live-dating`, switch `LIVE_DATING`)

Built on the extension points above; nothing of phase 1 changes shape.

- **Service** `live/dating.py` (`DatingFeature`, one line in `FEATURES`), words in `live/dating_content.py` (94
  icebreaker cards with 3–4 answers, a 16-item menu, quick chat lines). Frames: `queue {op: sit|stand|peek, pref,
  g, spot?}`, `answer {date, step, …}`, `heart {date, v}`, `date_say`, `date_leave`, `date_block`, `date_report`;
  pushes `bench`, `date` (always one player's own view), `bond`; the welcome carries `bonds`, `bench`, `date`.
- **Matcher** `match(seats, ok)` (pure): the oldest waiting player gets the oldest partner whose preference fits
  both ways (by the character's Nam/Nữ, which the client sends from its save; unknown fits only "ai cũng được"),
  online, not blocked (`blocks`, `marriage_blocks`; checked again in the database), not dated in the last 24 h
  (`live_dates`, reloaded at start). Buckets by (gender, preference): ~15 ms for 3,000 seats.
- **The date** (room `date:<id>`, cap 2): hello 4 s → 3 cards (40 s each, revealed together when both picked,
  4 s) → "Chọn món cho nhau" (60 s, 6 s reveal) → chat 60 s (or both "xong") → vote 30 s; ≤ 5 minutes. Votes are
  never sent; the end is `match` or `nope` (one frame for both). Leaving, blocking or 15 s without a socket ends
  it for both (`left` / `gone`, a gentle line). A reconnect lands back in the date. `LIVE_DATE_SPEED` (tests and
  the load test only) runs the clock faster.
- **Both ❤️**: `date_bonds` row ("Đang tìm hiểu 💕": `live.bonds` on the chat friend list, `dating` on the Bạn bè
  card from game/friends.py), friends both ways when both have an account (the `friends` rows), +5 tinh thần each
  through `effects.grant` (cap 15 a day).
- **Game side**: `game/live_dating.py` (SQLite twin of the two tables, `bonded()`, `forget()`), the tables in
  `game/pg_schema.py` (schema 6, created at start-up with the chat tables: `live_dates`, `date_bonds`), and
  **`game/live_effects.py`**, the applier described above: `on_load(store, token, state)` from `/api/bootstrap`
  after `system_gift.on_load`, internal action `sys_live`, request id `live-<id>`, ids kept in
  `journey['live_fx']` (last 60), kinds `coins` (wallet, the row's `data.label` or "🎈 Quà từ phố") and `spirit`.
  Phase 2's red envelope only needs `grant(db, sid, 'coins', n, key=…, data={'label': '🧧 …'}, cap=…)`.
- **Client** `public/js/v4/dating.js` + `public/css/dating.css` (lazy): entry points are the menu entry
  `liveDate` (`dateNav()` in live.js, next to Chat), the heart in the chat header, a "💕" pill on the scene while
  waiting or on a date, and a match that opens the dialog by itself.
- **Street bench (phase 2)**: when the stroll opens, app.js calls `live.js` `benchSpot(walk)`, which (dates on)
  registers `walk.addSpot({id:'dating-bench', place:'*', at:'bench', …})` from `dating.js` `addBench`: the bench of
  every public place glows with a 💗 / ⏳ / 💕 sign drawn on the canvas, and a tap opens Góc hẹn hò and sits down at
  once (`spot: 'street:<place>'`). Dates off: the tap just walks there.
- **Tests**: `tests/test_live_dating.py` (matcher, state machine, privacy, end frames, blocks, 24 h, leave,
  disconnect, reconnect, rewards), `tests/test_live_effects_apply.py`, `scripts/browser_live_dating.py`,
  `scripts/live_load.py --dates 200`. Measured locally (PostgreSQL 16, after the 1.0.0 merge): 2,000 sockets (500
  strolling, Cả phố at 5 messages/s) plus 200 dates at once (400 more sockets, real time, 90 s): Cả phố p95 16.5 ms,
  moves p95 94 ms, answer round trip p95 2.1 ms, date chat p95 2.3 ms, bench wait p95 63 ms, live process 13.7% of
  a core on average (peak 27%), RSS 95 MB, no errors. Ships as 1.0.1 with `SCHEMA_VERSION` 7 (the two tables).
