## Key decisions

- **One process, memory state, bounded.** `LIVE_MAX_CONN` (5,000) sockets, 5 per player, 40 per IP; channel ring
  buffers of 50 messages for at most 2,000 channels (LRU); member caches LRU; every limiter table pruned.
- **Identity.** pid = `sha256('pid:' + sid)[:16]` (the Phố nghề id, `game/social.pid_of`). Name: the account's
  display name, else the guest's character name (`leaderboard_players`), else the Phố nghề name. No name → can
  read, cannot post. Avatar: `profiles.avatar`. The service never reads a save.
- **Age** (new sessions read-only on Cả phố for 10 minutes): born before today (`stat_births`), else the oldest of
  `accounts.created_at`, `profiles.created`, the first `stat_play.first_at`.
- **Cả phố** is a room the client joins while it is on screen (`join {ch:"town"}`), so fan-out reaches viewers
  only. Slow mode 10 s per player (server-enforced; the error carries `wait`, the send button counts down).
- **DMs** need `friends` both ways and no block (`blocks` by pid or `marriage_blocks` by sid, either direction).
  Offline recipient → one `push_queue` row (kind `chat`, the player's `social` preference, ≤ 6 unsent) at most
  once per 10 minutes per chat (`chat_members.pushed_at`).
- **Groups**: owner creates, invites friends, ≤ 20 members, owner removes, members leave.
- **Messages are kept.** Delete own → text emptied, `deleted=1`. 3 distinct reports → `hidden=1` until an admin
  decides (`hidden=2` hidden, or back to 0; `reviewed_at` set). Admin changes reach the service by
  `NOTIFY mnl_live` (PostgreSQL); the service also re-checks its buffers when the LISTEN connection reconnects.
- **Restart.** SIGTERM → every socket gets close code 1012; clients reconnect with jitter and backoff 1, 2, 4… 15 s
  and resume with the last message id they hold per open channel (`hello {resume: {ch: id}}`).
- **Switches** `LIVE_CHAT`, `LIVE_STREET`, `LIVE_DATING` are read by the live service and sent in
  `welcome.flags`. All off → the service says so and closes; the client then waits 10 minutes before trying again.
  Before the first welcome ever arrives (no service yet), the client retries slowly (1 min → 10 min), so the game
  server never sees a reconnect storm.

1. **Python library** (on a machine with internet, or the server itself):
   `scripts/vendor_websockets.sh /opt/mot-ngay-lam-nghe/shared/pyvendor` (pure-Python wheel `websockets==17.1`,
   checks its sha256). psycopg is already there (`python3-psycopg` + pyvendor).

   `chat_channels`, `chat_members`, `chat_messages`, `chat_mutes`, `chat_prefs`, `live_effects`; nothing existing
   changes).

4. **systemd** `deploy/live/mnl-live.service` → `/etc/systemd/system/`, `systemctl daemon-reload`,
   `systemctl enable --now mnl-live`. `User=`/`Group=` and the sandbox lines must match `systemctl cat
   mot-ngay-lam-nghe`.
5. **nginx** `deploy/live/nginx-live.conf` (a `location = /live` block) in the `server {}` of
   `/etc/nginx/sites-enabled/phocochuyen`, `nginx -t`, `systemctl reload nginx`. Check `worker_connections`
   (each socket holds two nginx connections).
6. **Rolling releases** restart `mnl-live` after the game when the unit exists (`deploy/rolling_release.sh`;
   copy it to `/usr/local/sbin/mnl-rolling-release`).
7. Load test on the server before switching `LIVE_CHAT=1`: `scripts/live_load.py --url ws://127.0.0.1:8770/live
   --db-url ... --conns 2000`.

## Extension points for phases 2 and 3

- **Features** (`live/protocol.py`): a feature is an object with a name, a switch (`flag`: `chat`, `street`,
  `dating`), frame handlers registered with `@feature.on("move", rate=(4, 1.0))`, and optional hooks
  `welcome(conn)` (extra welcome fields), `on_hello(conn)`, `on_close(conn)`, `tick(now)` (called every second)
  and `on_notify(event)` (admin NOTIFY events). `live/app.py` registers `ChatFeature`; phase 2 adds
  `StreetFeature` (`live/street.py`), phase 3 `DatingFeature` (`live/dating.py`), each one line in
  `FEATURES`. A frame for a feature whose switch is off gets `error {code: "off"}`. Handler names are global:
  phase 2 owns `move`, `emote`, `say`, `sit`; phase 3 owns `queue`, `answer`, `heart`.
- **Rooms** (`live/hub.py` `Room`): a set of connections with a capacity, an optional ring buffer, and
  `send(frame, skip=…)` that serializes once and applies the slow-client cutoff and the block filter.
  `hub.room(id, cap=…)` creates or returns one; `hub.rooms_with_prefix("street:boho:")` lists instances so
  "join the fullest instance with room" is a few lines. Cả phố is `Room("town")`; a street instance would be
  `Room("street:boho:1", cap=20)`, a café table `Room("table:<id>", cap=4)`, a date `Room("date:<id>", cap=2)`.
  A room's `on_empty` callback lets a feature drop instance state.
- **Stored talk** (`ChatFeature.store_message(conn, channel, text)`): filters, mute check, duplicates, insert,
  returns the frame. Street speech bubbles and date chat reuse it with their own channel ids
  (`street:<place>`, `date:<id>`), so reports, admin hide and mutes work for them unchanged.
- **Presence** (`hub.online(pid)`, `hub.visible(pid)`, `hub.conns_of(pid)`): phase 2/3 know who is online and
  shown as online; the matcher pairs only online players.
- **Blocks** (`hub.blocked(a_pid, b_pid)`): both directions, `blocks` and `marriage_blocks`.
- **Rewards** (`live/effects.py` `grant(db, sid, kind, amount, key, data, cap)`): inserts a `live_effects` row
  (`id` = the idempotency key, status `pending`) when the daily cap for that kind allows it. Phase 3 adds
  `game/live_effects.py` `on_load(store, token, state)` called from `/api/bootstrap` beside
  `system_gift.on_load`, applying each pending row through `Store.command` with an internal action and the fixed
  request id `live-<id>` (the `system_gift` pattern: paid once), then `status='applied'`.
- **Client** (`public/js/v4/live.js`): `live.on(type, fn)` for any server frame, `live.send(frame)`,
  `live.flags`, `live.unread()`; an entry point is drawn only when its flag is on. The chat dialog
  (`v4/chat.js`) is separate; phase 2/3 add their own dialogs/scenes the same way.
