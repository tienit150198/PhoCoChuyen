## Follow-up: explicit close after POST /api/command

Read-only review of the additional `Handler.respond` condition and the expanded `tests/test_http_admission.py`; no tests were rerun. The parent reports 38 targeted tests passed.

- `urlsplit(self.path).path` matches the command route with a query string. The condition is restricted to POST, so GET/static reuse remains eligible for the idle timeout.
- Python's inherited `send_header('Connection', 'close')` both emits the header and sets `self.close_connection=True`. The handler still writes the complete Content-Length-framed response before returning and closing; the client can avoid reusing a socket that the server is closing.
- Successful commands and the command route's current JSON error paths all pass through `respond()`. The generic `extra` headers are emitted later, but no current command success/error path supplies a conflicting Connection header. A future caller must preserve that invariant; a later `Connection: keep-alive` would override the handler flag and create contradictory headers.
- On early rejection before reading the body, `discard_body()` sees the intentional close and skips draining. No unread bytes are interpreted as another request, and a client that has not finished uploading cannot retain the slot through a body-drain wait. Existing body framing and response-write timeout remain unchanged.
- Closing each command also means requests pipelined after that command are not processed on the same socket. This is the advertised HTTP connection policy, not continued command pipelining support.
- The tradeoff is a fresh backend TCP connection/handler thread per command, with associated accept, scheduling and TCP lifecycle costs. With the documented terminating reverse proxy, Connection is a hop-by-hop upstream policy; it does not inherently force a fresh browser TLS/HTTP2 connection. Direct connections to the Python server do reconnect per command. The production proxy configuration and complete workload still require measurement; the earlier failed soak and diagnostic numbers do not establish that this latest version meets all acceptance targets.

**Prior documentation finding (P3), resolved:** `docs/DEPLOY.md:117` now explains that POST `/api/command` closes immediately after its response, independent of `HTTP_KEEPALIVE_SECONDS`, and describes the fresh upstream TCP/thread cost and the distinction from browser TLS when a reverse proxy terminates TLS.
